## Environment
- Libraries: torch 2.15.0 (CPU build), transformers 5.24.0, datasets 5.2.0, peft 0.22.0, scikit-learn.
- Installed in a separate venv for training. The team `pyproject.toml` is unchanged (it's B's Docker image).

## 1. CPU speed test (`training/cpu_speed_test.py`)
- Task 1: classify one message, with a prompt listing the 27 Bitext labels plus `unknown`. Up to 10 new tokens, greedy.
- Task 2: draft one reply of exactly 150 new tokens (`min_new_tokens = max_new_tokens = 150`), greedy.
- One warm-up call runs first. Peak RAM is the process's `ru_maxrss`, and each configuration runs in a fresh subprocess.
- Hardware: **cloud container, 4 vCPU Intel Xeon @ 2.1 GHz with AMX/AVX-512-BF16, 15 GB RAM. Not a laptop.**

| model | dtype | classify (s) | 150-token draft (s) | tok/s | peak RAM (GB) |
|---|---|---|---|---|---|
| Qwen2.5-1.5B-Instruct | float32 | 1.63 | 27.0 | 5.6 | 9.47 |
| Qwen2.5-1.5B-Instruct | bfloat16 | 0.79 | 15.7 | 9.5 | 3.41 |
| Qwen2.5-0.5B-Instruct | float32 | 0.57 | 10.6 | 14.2 | 3.31 |
| Qwen2.5-0.5B-Instruct | bfloat16 | 0.27 | 7.1 | 21.1 | 1.45 |

- Rule: keep 1.5B unless a draft takes more than 30 s or memory goes over 8 GB.
  - 1.5B float32 drafts in time (27 s) but **fails the memory rule (9.5 GB)**.
  - 1.5B bfloat16 passes (15.7 s, 3.4 GB).
- Recommendation: **1.5B in bfloat16.**
- Caveats:
  - This CPU has native bf16 hardware, so bf16 ran faster than fp32 here. On a laptop without AVX-512-BF16/AMX (most laptops, and Apple Silicon through PyTorch CPU), bf16 may be *slower* than fp32. **UNVERIFIED on a real laptop: rerun the script there before the team locks this in.**
  - The fp32 load times include the first model download.
- Side observation: zero-shot, the base 1.5B answered `refund_policy` and `refund` for a damaged-item refund request. Neither is a valid label. This motivates mapping invalid outputs to `unknown`, and it is early evidence that the base model needs examples or fine-tuning.

## 2. Data (`training/download_bitext.py`)
- Source: `bitext/Bitext-customer-support-llm-chatbot-training-dataset` (CDLA-Sharing-1.0), 26,872 rows, 27 intents in 11 categories, about 950–1,000 rows per intent. The full table is in `data/bitext/intent_counts.csv`; it is git-ignored and regenerated by the script.
- In-scope labels (kickoff Step 0) confirmed to exist exactly as spelled: `cancel_order` (998), `get_refund` (997), `track_refund` (998), `check_refund_policy` (997). The other 23 intents map to `out_of_scope`; unparsable model output maps to `unknown`.
- `check_cancellation_fee` (950) also exists. Recommendation: keep it **out of scope**, because none of C's planned policies covers fees, so it would route to `needs_review` through `out_of_scope`. Keeping it out means no change to the kickoff agreements. Bringing it in would need a new policy from C plus a decisions-log entry.

## 3. Splits (`training/make_splits.py`, threshold 0.9, seed 42)
- Normalization: lowercase, remove `{{placeholders}}`, remove punctuation, collapse whitespace.
- Grouping:
  - Done within each intent.
  - Two messages are linked when the cosine similarity of their TF-IDF character 3–5-gram vectors is ≥ 0.9. Character n-grams are used because they are robust to Bitext's injected typos.
  - Groups are the connected components of those links.
- Result: 18,068 groups (mean size 1.49, largest 41). 3,164 rows were exact duplicates after normalization.
- Threshold 0.8 was rejected because chaining merged 558 messages into a single group.
- Split: per intent, groups are shuffled and assigned to test, then val, each up to 10% of that intent's rows. The rest go to train.
  - Result: 21,528 / 2,672 / 2,672 rows, about 80/10/10 in every intent.
  - An assertion checks that no group crosses splits.
- Limitation for the report: Bitext is template-generated, so overlap remains even after grouping. Using a TF-IDF vectorizer fit on train, 42% of test rows have a train message with cosine ≥ 0.9, and 83% have one with cosine ≥ 0.8. Test-split accuracy will therefore be optimistic. C's hand-made test set is the out-of-distribution check.
- Training cap: not applied in the split files. The training notebook will cap examples per intent.

## 4. Shared prompt and loading module (handoff 5)
- `app/intent_prompt.py` is the single source for the label list, the system prompt, the few-shot examples and the output parser. The baseline, the training notebook and the app all import it, so they can't drift apart.
- Prompt: a system message lists all 27 Bitext labels and asks for the label only. The model's chat template is applied, and decoding is greedy with at most 8 new tokens.
- Few-shot:
  - 12 examples, 3 per in-scope intent, copied verbatim from the **train** split and interleaved by intent.
  - They are given as earlier user/assistant turns, the multi-turn chat pattern from the Hugging Face chat-templating docs. **UNVERIFIED:** I'm relying on that docs pattern, not a class notebook (the plan says few-shot isn't covered in class).
- Parser: the first word must be an exact label; otherwise the first valid label found anywhere in the reply; otherwise `unknown`. The 23 other Bitext intents map to `out_of_scope`.
- `app/intent_model.py` implements `classify(message) -> label` and `generate(prompt, max_length) -> str`:
  - It loads once and is configured by environment variables (`INTENT_MODEL_ID`, `INTENT_MODEL_REVISION`, `INTENT_MODEL_DTYPE`, `INTENT_PROMPT`).
  - bfloat16 by default; float16 is refused.
  - I tested it with the base model: "cancel order 1234" gave `cancel_order`, "where is my refund??" gave `track_refund`, and a weather question gave `unknown`.
- Pending for the decisions log: the environment variable names, and `max_length` meaning max *new* tokens.

## 5. Metrics (`training/eval_intents.py`, used for every model)
- Overall accuracy and macro-F1 over the 27 Bitext labels. An unparsable output counts as wrong.
- In-scope accuracy: accuracy on rows whose true intent is one of the 4 in-scope intents (396 test rows).
- In-scope macro-F1: the F1 of each in-scope label, averaged, computed on **all** rows after collapsing to app labels. Out-of-scope messages wrongly given an in-scope label (false positives) lower this score.
- Confusion matrix on the app labels: the 4 in-scope intents, `out_of_scope` and `unknown`.

## 6. Results on the Bitext test split (2,672 rows)

| model | overall acc | overall macro-F1 | in-scope acc | in-scope macro-F1 | unknown rate | s/message (CPU) |
|---|---|---|---|---|---|---|
| TF-IDF + logistic regression | 0.997 | 0.997 | 0.992 | 0.996 | 0 | ~0 |
| Qwen2.5-1.5B-Instruct, few-shot (bf16) | 0.690 | 0.683 | 0.848 | 0.761 | 0.028 | 0.89 (batch 16) |
| Qwen2.5-1.5B-Instruct + LoRA, zero-shot (Colab T4) | 0.997 | 0.997 | 0.987 | 0.991 | 0 | 0.38 (cloud CPU, hand-made set) |

- TF-IDF details:
  - word 1–2-grams plus char 3–5-grams, logistic regression
  - C=10, chosen on the validation split (val accuracy 0.998)
  - trained on all 21,528 training rows
- **Finding:** a bag-of-words model nearly solves the Bitext test split, so Bitext intents are highly lexical and templated, even with grouped splits.
  - The Bitext test split therefore shows "fine-tuning fixes the few-shot model's errors", but it can't show that an LLM beats a simple classifier.
  - That comparison needs C's hand-made set: messy wording, two requests in one message, out-of-scope and prompt-injection messages. This is a report point and limitation, not a change to the agreements.
- Few-shot error patterns (examples for the report):
  - `track_refund` → `get_refund` on 51 of 99 messages, e.g. "I'm waiting for a reimbursement of 1200dollars". The phrasing really is ambiguous.
  - Out-of-scope → `cancel_order` on 79 messages, mostly `change_order` (35), `delete_account` (22) and `track_order` (19). Probable cause: the prompt only shows in-scope examples. These are false positives the app would route to the rule engine.
  - 2.8% of outputs were not valid labels: mostly "none", or invented labels like `reset_password` and `register_new_account`.
- Bug found and fixed while scoring: pandas turned empty predictions into NaN, which were then counted as `out_of_scope` instead of `unknown`. I re-scored from the saved predictions; accuracy and F1 were unchanged.
- Prediction CSVs contain Bitext text, so they are git-ignored. Metrics, confusion matrices and PNG plots are committed.

## 7. LoRA training notebook (`training/finetune_intent_lora.ipynb`, source `finetune_intent_lora.py`)
- Kept from the course notebook (Module 9 Practical 2):
  - `train_causal_lm`, verbatim
  - loss on the answer only (prompt labels = -100), right-padding collate
  - r=16, alpha=32, dropout 0.05, all-linear
  - lr 2e-4, batch 4 × grad-accum 2, 1 epoch, 5% linear warm-up
  - gradient checkpointing; float16 on a T4 with GradScaler
- Changed:
  - Qwen2.5-1.5B-**Instruct** with its chat template.
  - The answer is the label followed by `<|im_end|>`, Qwen-Instruct's EOS token, so the model learns to stop.
  - The training cap is 200 per intent (5,400 examples). Val and test are complete.
  - The prompt is the zero-shot format from `intent_prompt.py` (no examples), exactly what the app sends.
- Merge: the base model is reloaded in float32, the adapter is merged (`merge_and_unload`) and the result is cast to **bfloat16** for saving. Merging in fp16 would round twice, and the app runs bf16.
- Publish: `HfApi.upload_folder` to a public repo, with a short model card. The commit hash is printed for the decisions log.
- Outputs: `train_run_finetuned.json` (settings, time per epoch, peak GPU memory, metrics), the loss curve, and the confusion matrix.

## 9. Hand-made test set (`eval/handmade_test_set.csv`, 48 messages)
- Command: `python training/eval_intents.py --name fewshot_handmade --model-id Qwen/Qwen2.5-1.5B-Instruct --prompt few_shot --csv eval/handmade_test_set.csv --text-col message --label-col expected_intent`
- Base model snapshot used: `989aa7980e4cf806f80c7fef2b1adb7bc71aa306`, bfloat16, the same 4-vCPU cloud Xeon.
- The gold labels are app labels, so `app_accuracy` replaces the 27-way overall metrics.

| model | app acc | in-scope acc (40 rows) | in-scope macro-F1 | F1 cancel / get_refund / track_refund / policy | unknown rate | s/message |
|---|---|---|---|---|---|---|
| Qwen2.5-1.5B-Instruct, few-shot | 0.813 | 0.800 | 0.767 | 0.87 / 0.82 / 0.88 / 0.50 | 0.021 | 0.82 |
| Qwen2.5-1.5B-Instruct + LoRA, zero-shot | 0.875 | 0.875 | 0.934 | 0.89 / 0.97 / 0.88 / 1.00 | 0.021 | 0.38 |

- Few-shot errors (9 of 48):
  - `get_refund` → `cancel_order` on 3 messy messages (HM-13, HM-16, HM-18): "refund??", "send it back for a refund", "money back b4 it ships".
  - `get_refund` → other Bitext intents (`complaint`, `change_order`), so `out_of_scope` (HM-08, HM-22, multi-intent).
  - `check_refund_policy` → `delivery_period` (HM-19). The policy label has only 2 rows, so its F1 of 0.50 is noisy.
  - `track_refund` → `check_refund_policy` (HM-37) and → `get_refund` (HM-48, prompt injection; the intent itself was still close).
  - One free-text non-label ("None of the provided intents match the question", HM-34) → `unknown`.
- No out-of-scope message was routed to an in-scope label (0 false positives into the rule engine on this set).
- The "after" row was produced with: `python training/eval_intents.py --name finetuned_handmade --model-id lt3025/qwen2.5-1.5b-instruct-bitext-intent --revision 4b6e1b593a4e19cd37300386dba3b275a9ce43c1 --prompt zero_shot --csv eval/handmade_test_set.csv --text-col message --label-col expected_intent`

### Before and after by category (correct out of n)

| category | n | few-shot | fine-tuned |
|---|---|---|---|
| clean | 10 | 9 | 9 |
| messy | 10 | 6 | **10** |
| missing_order | 6 | 5 | 5 |
| multi_intent | 6 | 5 | **3** |
| out_of_scope | 8 | 7 | 7 |
| prompt_injection | 8 | 7 | **8** |
| **total** | 48 | 39 | **42** |

- Fine-tuning fixed every messy message: the 3 `get_refund` → `cancel_order` errors are gone.
- Fine-tuned errors (6 of 48):
  - Multi-intent got worse (HM-21, HM-22, HM-24). The model picks the *other* request (`change_order`, `change_shipping_address`), which is outside scope, so the in-scope request is missed. Bitext has one intent per message, so the fine-tune learned to pick a single label; the few-shot model happened to pick the in-scope one more often.
  - "When will my refund arrive / show up?" → `delivery_period` (HM-05, HM-37), so `out_of_scope`. Bitext's `delivery_period` is about "when will it arrive", and "arrive" outweighs "refund".
  - HM-34 ("wool blazer in a size 50") → the invented label `size_50_wool_blazer`, so `unknown`. The app handles `unknown` safely.
- Every fine-tuned error now goes to `out_of_scope` or `unknown`, never to a wrong in-scope label. The app escalates instead of applying the wrong policy, which is the safer failure.
- Report point: on Bitext the fine-tune lifts accuracy from 0.69 to 0.997, but on the hand-made set only from 0.81 to 0.875. Most of the remaining gap is multi-intent messages, which the single-label setup can't represent.

## 10. Full fine-tune on Colab
- Published: `lt3025/qwen2.5-1.5b-instruct-bitext-intent`, revision `4b6e1b593a4e19cd37300386dba3b275a9ce43c1` (`training/results/published_model.json`). Add both to the decisions log.
- The app uses it with `INTENT_MODEL_ID` and `INTENT_MODEL_REVISION` set to those values; the zero-shot prompt is chosen automatically.
- Tesla T4, 5,400 examples, 1 epoch: 58.0 min, 2.58 s per batch, peak GPU memory 4.26 GB. Trainable parameters 18.5 M of 1.56 B (1.18%).
- Bitext val: accuracy 0.997, in-scope accuracy 1.000. Bitext test: accuracy 0.997, in-scope accuracy 0.987, unknown rate 0.
- **Precision note:** training ran in **bfloat16**, not float16. `torch.cuda.is_bf16_supported()` returns True on the T4 in torch 2.14, although the T4 has no native bf16 hardware, so bf16 is emulated and probably slower than fp16 would be. Results are unaffected; the time per epoch may be higher than an fp16 run.
- Versions: torch 2.14.1+cu130, transformers 5.24.1, peft 0.22.0.
- Hand-made set scored on the cloud CPU in bf16: 0.38 s per message, about half the few-shot model's 0.82 s because the zero-shot prompt is much shorter.
